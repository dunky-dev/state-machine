Targets Vue 3.3 and later (`vue` `^3.3.0`). The bridge uses only the reactivity and lifecycle APIs both Vue renderers share, so it also runs inside Vue 3.6's Vapor components (verified on the release candidate).

The Vue package is a thin edge layer. Behavior lives in the core machine and the component's `connect` function; this package only adapts them to Vue: lifecycle, reactivity, prop translation, and platform effects. **The machine itself is unchanged** — the same `createDialogConfig` and `connectDialog` run here as on any other target.

The connector's snapshot is exposed as a **computed ref**: a template unwraps it (`api.isOpen`), script reads `api.value.isOpen`, and it changes only when the machine or the props do.

## `useMachine`

The one bridge composable. Every component calls it with the four agnostic pieces and gets back `{ api, machine }` — the view API to render from, and the running service (for `send` and `useSelector`):

```vue
<script setup lang="ts">
import { useMachine, normalize } from '@dunky.dev/vue-state-machine'
import { createDialogConfig, connectDialog, dialogEffects, type DialogProps } from './dialog'

const props = withDefaults(defineProps<DialogProps>(), {
  open: undefined,
  closeOnEscape: undefined,
})

const { api } = useMachine(
  createDialogConfig, // (props) => MachineConfig; seeds context once
  connectDialog, // pure connect(): snapshot → view api
  dialogEffects, // ComponentEffect[]: DOM listeners, gated by props
  props,
)
</script>

<template>
  <button v-bind="normalize(api.triggerProps)">Open</button>
  <div v-if="api.isOpen" v-bind="normalize(api.contentProps)">Dialog content</div>
</template>
```

`useMachine` builds the machine and connector **once** (`setup()` runs once per instance, so the first props seed context; later changes flow through `setProps`, not a rebuild), starts after mount, stops on unmount, and exposes the connect output as a computed ref. Inside `<KeepAlive>` it pauses while deactivated — the machine stops and its effects are torn down, then both resume with state intact — and on the server nothing starts: `renderToString` renders the initial snapshot. In an async `setup()`, call it before the first `await`: Vue only binds lifecycle hooks registered before it.

### Boolean props

Vue casts an **absent** `Boolean` prop to `false`, but the machine reads `undefined` as "not set". Left as-is, `open` would always look controlled and a `modal: true` default would be lost, so declare every boolean prop with `default: undefined` — as in the `withDefaults` call above, or `{ type: Boolean, default: undefined }` in a runtime declaration.

### The three imports

Those three values are where the dialog's behavior actually lives, and none of it is Vue. You write them once, in a `./dialog` module, and they run unchanged on any platform:

```ts
// dialog.ts: plain functions, no Vue
import { setup, type Connect } from '@dunky.dev/state-machine'

export type DialogProps = {
  open?: boolean
  onOpenChange?: (open: boolean) => void
  closeOnEscape?: boolean
}

type State = 'closed' | 'open'
type Context = { closeOnEscape: boolean }
type Event = { type: 'open' } | { type: 'close' }
type Api = {
  isOpen: boolean
  triggerProps: object
  contentProps: object
}

export const createDialogConfig = (props: DialogProps) =>
  setup.infer().createMachine({
    initial: props.open ? 'open' : 'closed', // props seed the machine ONCE
    context: { closeOnEscape: props.closeOnEscape ?? true },
    states: {
      closed: { on: { open: { target: 'open' } } },
      open: { on: { close: { target: 'closed' } } },
    },
  })

export const connectDialog: Connect<State, Context, Event, DialogProps, Api> = ({
  state,
  send,
}) => ({
  isOpen: state === 'open',
  triggerProps: {
    onPress: () => send({ type: 'open' }),
    expanded: state === 'open',
  },
  contentProps: { role: 'dialog', modal: true },
})

export const dialogEffects = [onEscapeKey]
```

So `useMachine` is the only Vue-specific piece: `createDialogConfig` is the machine definition, `connectDialog` is the snapshot-to-view-API mapping, and `dialogEffects` are the DOM listeners. Every target imports the **same** `./dialog` module — only the bridge differs. See [Setup](/api/setup) for configs and [Connector](/api/connector) for how `connect` works in depth.

## `normalize`: bindings → DOM props

`connect` returns substrate-agnostic bindings (`onPress`, `role`, `describedBy`). `normalize` translates them to the DOM/ARIA props `v-bind` and `h()` take:

```ts
normalize(api.value.triggerProps)
// { onClick, 'aria-expanded', role, tabindex, ... }
```

The machine binding maps handlers (`onPress` → `onClick`), ARIA props (`describedBy` → `aria-describedby`), ARIA state (`checked` → `aria-checked`), and focus (`focusable` → `tabindex`). Multi-word events use Vue's listener casing — `onPointerenter`, `onKeydown` — because Vue derives the DOM event by hyphenating the camel tail (`onPointerEnter` would listen to `pointer-enter`). [Check out the full mapping here](https://github.com/dunky-dev/state-machine/blob/main/packages/vue/src/normalize.ts).

`undefined` values are dropped. Unknown keys pass through unchanged.

## `mergeProps`: consumer + component props

When a consumer's props land on the same element the component controls:

```vue
<script setup lang="ts">
import { useAttrs } from 'vue'
import { mergeProps, normalize } from '@dunky.dev/vue-state-machine'

defineOptions({ inheritAttrs: false })
const attrs = useAttrs()
// …useMachine as above
</script>

<template>
  <button v-bind="mergeProps(attrs, normalize(api.triggerProps))">Open</button>
</template>
```

- **Event handlers are chained, consumer-first.** If the consumer calls `e.preventDefault()`, the component's handler is skipped — a clean veto. An array of consumer handlers composes like one.
- **`class` and `style` are merged** into a `[consumer, library]` array, whatever shape each side uses; Vue normalizes it, and the library's style wins a conflicting key.
- **Everything else: component wins** (`id`, `role`, `aria-*`).

Turn `inheritAttrs` off when you spread `useAttrs()` like this, or Vue also falls the attrs through to the root element and every handler runs twice. Don't confuse this with Vue's own `mergeProps` from `vue`, which concatenates handlers with no veto.

## `useSelector`: fine-grained leaf subscription

For a leaf component that should only re-render when one slice of the machine changes (useful when a single machine drives many rows and each row should only wake for its own value). It returns a **readonly ref** — a template unwraps it:

```vue
<script setup lang="ts">
import { useSelector } from '@dunky.dev/vue-state-machine'
import type { RowMachine } from './row'

const props = defineProps<{ machine: RowMachine; value: string }>()

const isHighlighted = useSelector(
  props.machine,
  () => props.machine.context.highlightedValue === props.value,
)
</script>

<template>
  <div :data-highlighted="isHighlighted">{{ value }}</div>
</template>
```

The ref updates only when the selected value changes — `Object.is` by default. For object selections, pass a custom equality function so a re-derived equal object doesn't bump the ref:

```ts
const pos = useSelector(
  machine,
  () => ({ x: machine.context.x, y: machine.context.y }),
  (a, b) => a.x === b.x && a.y === b.y,
)
```

The selected value comes back as-is, never wrapped in a reactive proxy, and the subscription is disposed with the component — or with the surrounding `effectScope()`.

## `ComponentEffect`: platform effects

Some behavior can't live in the machine because it touches the DOM or reads props the machine never sees. Declare each as a `[setup/teardown, depPropNames]` tuple; `useMachine` runs each entry after mount and re-runs it (cleanup → setup) when one of its named prop deps changes:

```ts
import type { ComponentEffect } from '@dunky.dev/vue-state-machine'
import type { DialogMachine, DialogProps } from './dialog'

type Effect = ComponentEffect<DialogMachine, DialogProps>

const onEscapeKey: Effect = [
  (machine, props) => {
    if (!props.closeOnEscape) return
    const handler = (e: KeyboardEvent) => {
      if (e.key === 'Escape') machine.send({ type: 'close' })
    }
    document.addEventListener('keydown', handler)
    return () => document.removeEventListener('keydown', handler)
  },
  ['closeOnEscape'], // re-run only when this prop changes
]

export const dialogEffects = [onEscapeKey]
```

The tuple shape is **identical to every other target** — the same `./dialog` effects run everywhere. The deps are prop NAMES (typed `(keyof Props)[]`, so a typo is a compile error); the Vue bridge watches exactly those props, compares each by value, and re-runs after the DOM update, so a prop the effect merely reads never becomes a hidden dependency. As on React, effects start once the machine has, and are cleaned up after it stops. The machine only receives `send({ type: 'close' })`; it has no idea a keyboard event exists.

See [Effects](/api/effects) for the full mental model of where each type of effect lives.
