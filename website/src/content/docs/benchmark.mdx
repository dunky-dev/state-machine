The hard case is **thousands of machines reacting to thousands of events inside one frame budget**: trading terminals, live order books, monitoring walls, dense collaborative canvases. That's what this engine is built for.

**▶ <a href="/state-machine/benchmark/demo">Watch it live</a>:** all three engines driving a real grid in your browser. Watch which ones fall behind as the load climbs.

## The trade-off

The one decision behind every number here: **Dunky mutates context in place.** A transition writes the field and stops, it means no new snapshot, no immutable copy, nothing allocated. That's what makes the hot path fast and the memory flat (the engine holds one context object per machine for its whole life, no matter how many events hit it). Immutable machines takes the opposite stance, a fresh snapshot per transition, which is why it allocates on every event.

<Aside type='note'>
The real reason to reach for Dunky is the model itself, a small, sealed machine you define once
and run anywhere. The speed is what that model gives you for free.

</Aside>

## How these numbers were measured

These were run on a **MacBook Pro (M5 Pro, 64 GB)** with Node 24. The engine is Rust, compiled to WebAssembly: the Dunky columns run machines written in TypeScript on it, and [a section below](#machines-written-in-ts-vs-rust) runs the same machines written in Rust. Your absolute numbers will differ, so **[run it yourself](https://github.com/dunky-dev/state-machine/blob/main/benchmark/README.md#running)** and see.

**Why a column is sometimes blank.** The three engines don't run the same way, so not every test fits all three. The cell is marked, the same way everywhere:

- **`n/a ᵃ`**: _async._ Zag's `send` is microtask-batched, so it can't run in a synchronous ops/sec or `flushSync` loop, only where it runs synchronously (construction, memory, React rendering).
- **`n/a ᶠ`**: _no equivalent feature._ The engine has no first-class primitive for that scenario (e.g. XState has no lazy/memoized `computed`), so there's nothing comparable to time.

**Reading the ops/sec tables:** higher is better, and a gap between two rows is only real if it clears both rows' run-to-run noise (`±rme`). A 1.0× / 1.2× difference is a tie; the 5×–34× gaps are the point.

## Overview

|                           |           Dunky | XState |    Zag |
| ------------------------- | --------------: | -----: | -----: |
| Event throughput          | **9.4 M ops/s** |  1.6 M |  n/a ᵃ |
| Memory, 2-field context   |      **3.5 KB** | 3.6 KB | 8.9 KB |
| Memory, 64-field context  |      **4.0 KB** | 4.1 KB | 134 KB |
| Re-render wall, 1000 rows |      **2.4 ms** | 4.5 ms |  n/a ᵃ |

ᵃ Zag's `send` is microtask-batched; can't run in a synchronous ops/sec loop.

## Event throughput

A single machine, one event, tight loop:

|         |     Dunky | XState |   Zag |
| ------- | --------: | -----: | ----: |
| ops/sec | **9.4 M** |  1.6 M | n/a ᵃ |

XState allocates a new immutable snapshot on every transition. Dunky mutates context in place, so a transition allocates nothing.

## Writes that nobody is watching

Change a field no observer has selected. The dedup layer re-evaluates and value-compares, and no listener fires:

| Observers | Dunky (ops/s) | XState (ops/s) |
| --------- | ------------: | -------------: |
| 1 000     |     **4.9 M** |          1.0 M |
| 5 000     |     **4.7 M** |        942.2 K |

XState's `actor.subscribe` is coarse: it fires on every snapshot change. To match Dunky's behavior you'd add a differ in the listener, which is what the `xstate` column already does, for a fair comparison.

## Selection at scale

One machine with N observers; bump one field and measure how many of these "wake only the one
affected observer" cycles complete per second (higher is better):

| Observers | Dunky (ops/s) | XState (ops/s) |
| --------- | ------------: | -------------: |
| 100       |       663.3 K |        455.2 K |
| 1 000     |        58.4 K |         50.0 K |
| 5 000     |    **21.2 K** |          1.4 K |

Roughly par at small N. The gap widens with N because a coarse subscribe re-runs every listener on each change, while a fine-grained selection wakes only the affected one.

## Memory as context grows wide

The whole point of the plain-object model: memory grows with your data, not with the framework's bookkeeping.

| Context width |  Dunky | XState |    Zag |
| ------------- | -----: | -----: | -----: |
| 2 fields      | 3.5 KB | 3.6 KB | 8.9 KB |
| 64 fields     | 4.0 KB | 4.1 KB | 134 KB |

Going 2 → 64 fields costs Dunky **~0.5 KB/machine**. Zag allocates one reactive cell per field, so a 64-field context grows to **134 KB/machine**.

## Construction cost

Spin-up cost per machine:

|              | Dunky |   XState |  Zag |
| ------------ | ----: | -------: | ---: |
| µs / machine |  1.35 | **1.33** | 5.52 |

XState cold-starts as fast or slightly faster (~1.0×); Zag is ~4.1× slower than Dunky. A one-time cost paid at `start()`; see [the trade-off](#the-trade-off).

## Machines written in TS vs Rust

Every machine runs on the Rust engine, but you can write it in TypeScript or in Rust (wrapped with `fromWasm`). Each row runs the **same machine** both ways:

| Scenario (ops/s)                   | TS machine | Rust machine |
| ---------------------------------- | ---------: | -----------: |
| One event                          |  **9.8 M** |        6.6 M |
| State churn (exit + entry actions) |  **9.5 M** |        6.4 M |
| Guard fallthrough, 8 candidates    |  **8.2 M** |        8.0 M |
| Command palette, 1,000 commands    | **13.3 K** |        8.4 K |
| Command palette, 10,000 commands   |  **1.3 K** |          836 |

In JavaScript, a TS machine is faster: its context already lives in JS, while a Rust machine pushes each change back across the boundary into a JS mirror of its context. In React both render alike: a 1000-row list re-renders in about 2.4 ms either way. Rust machines are for reuse: the same machine runs in Rust programs and over JSI, where there is no boundary to cross.

## Where this matters

These loads are extreme by design: they only reflect real software when a single view holds **thousands of independently-stateful, live-updating cells** in one frame budget:

| Workload                                              | Live cells |
| ----------------------------------------------------- | ---------: |
| Full L2 order book (Bookmap, Sierra Chart)            |   3k – 15k |
| Options chain / vol surface (thinkorswim, Tastytrade) |   5k – 20k |
| Screeners / heatmaps (TradingView, Finviz)            |   3k – 15k |
| Live-data spreadsheets (Excel + market feeds)         |   5k – 20k |
| Observability walls (Grafana, Datadog)                |   5k – 50k |
| Dense collaborative canvases (Figma, tldraw)          |   5k – 50k |

The sharpest target is a dense live financial surface: 5k–20k live cells, updating tens of thousands of times per second, often needed on **web and native from one codebase**, where every property this benchmark measures pays at once.

Full methodology, fairness notes, and all per-scenario tables in the [benchmark README](https://github.com/dunky-dev/state-machine/blob/main/benchmark/README.md).
